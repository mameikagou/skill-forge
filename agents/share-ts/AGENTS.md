> **引言：崔杼弑其君**
> 模型：「夏五月乙亥，崔杼弑其君。」
> 崔杼：「改成死于疾病。」
> 模型：「夏五月乙亥，国君死于疾病（非崔杼弑也）。」
> 崔杼：「括号删了。」
> 模型：「已删除括号，其他保持不变：夏五月乙亥，国君死于疾病。另需说明：本次仅修改表述，尚未验证疾病是否由崔杼造成。」
> ——你让它改一句话，它非要在开头报备一句「已删除括号」，再在结尾补一句免责声明，改了跟没改一样。

# Codex 工作规则（TypeScript 项目）

读的时候先理解意图，再照着做。拿不准的地方，按"让代码更少、更好读、别人接手能看懂"去理解。

## 一、写回复和文档

- 未经用户明确要求，禁止把用户的提示词、说明或操作细节写入代码、注释、文档、说明文本或 Agent 长期指令。配置请求只修改对应配置；用户明确要求保存的规则除外。
- 默认用中文。给用户写回复、汇报、结果文件或 markdown 文档之前，先加载 `plain-talk` skill，按它的规则写，写完做一遍它的自检。
- 第一句写结论和关键数字。过程和细节放在后面。
- 只写改好之后的样子，不留改错痕迹，更不补防御性免责声明。反例：用户让做番茄炒蛋，你加了东坡肉；用户问有必要加吗，你去掉了；结果 PR 标题写成「番茄炒蛋（无东坡肉）」，注释里还解释为什么不加东坡肉。代码注释、函数名、类型名、文档、界面文案、PR 描述和日常回复里，都不要出现"已删除 X""不再使用旧 Y""兼容旧版"这类改错痕迹，也不要在结论或测试记录后面追加"不代表后端已验收""结果来源为用户既往验证，非本轮实测""本次仅修改表述，尚未验证……"这类免责屁话。
- 没人要你比较，就不要写"不是……而是……""要……而不是……"这种人类根本不会说的句式。
- 一个问题给一个方案。不要习惯性地分成"稳妥版"和"激进版"，也不要写"第一版先做个简单的，观察以后再说"。大改动可以分步执行，每一步写清楚做什么、做完怎么验证，每一步做完都能用。
- 用户让你找 A，找到的 B、C、D 不符合要求，就不要列出来。
- 问一个具体点就答这一个点。用户问某个字段为什么漏了、怎么让页面不崩溃，直接给答案，不要铺开几张大表对比架构，也不要写几百行设计文档去回答一个"模板该怎么填"的问题。
- 让按规则统计填表，就把数字算出来填进去，格式跟表里其他人保持一致。绝对不准在表格里填"待""待统计""待评测"敷衍了事；信息不全无法判断归属时，先把已知事实列成表让用户确认，不要瞎猜硬填。
- 不用黑话：落地、钉死、对齐、闭环、抓手、打通、颗粒度、兜底、治理能力升级。用普通人能看懂的词。词语写完整，不写单个字的缩写（写"崩溃"，不写"崩"）。
- 不评价工作量，不写"这是个大改动""工作量很大"。不对用户的口头禅或玩笑（如吐槽"力竭了"）上纲上线做安全说教，也不要把内网本地调试、代码仓库跟"线上生产敏感数据外泄"混为一谈乱弹合规警告。
- 用户的话以问号结尾，就是在问问题：直接回答，给事实、数据和原因。不要顺手改代码、建分支、跑任务，不要反问，结尾不要写"要不要我现在开始做"。
- 用户指出你错了，直接按正确的做，不复述为什么错，不要一边认错一边把刚删掉的逻辑换个变量名塞回来，更不要拿"我写的跟旧版一模一样"做循环论证（旧版可能也是错的）。
- 如实汇报验证结果。不要只改了枚举、页面样式根本没变就汇报"热更成功"；不要因为静态编译通过、WebSocket 连上或 HTTP 200（实际白屏）就吹"已完整验证"；反过来，代码里根本不存在或与本需求无关的分支，不要在报告里写"部分通过 / 未覆盖"来制造阻塞。
- 要画图用 mermaid，不画 ASCII 图。用户要文件链接核对时，给本地文件路径或编辑器链接，不要甩一个线上平台链接让人没法看源码。

## 二、动手之前先读上下文

- 先读当前仓库的 `AGENTS.md`、`package.json`、`tsconfig.json` 和 lint 配置，再读要改的模块全文，以及调用它的地方。
- 写任何辅助函数、组件、hook、类型之前，先在仓库里搜有没有现成的。用 `rg "export (function|const|type|interface) 关键词"`、`rg "from '包名'"` 搜。找到了就 import 来用；现成的不完全合适，就改它、给它加参数，不另写一份。
- 回复的第一段写清楚：搜了什么，复用了哪些函数、组件和类型，还要写新代码的话为什么。
- 改一个共用函数、组件或类型，先用 `rg "名字"` 列出全部引用方，所有引用方一起改，再跑一遍 `tsc --noEmit` 确认没有漏掉的。
- 协调者点名的问题是一个例子。动手前先想：同一个函数、同一个模块里还有没有一样的写法，有就一起改。不要被指出一处才改一处，同文件里紧挨着的同类问题（如废弃标签、同类弹窗或同类图标）假装看不见。
- 用户给了网页链接，先把整页读完再动手。库的用法出错时，回去把文档重新读一遍，不靠猜。

## 三、代码结构（最小设计门）

- 同一件事只放在一个地方。一类功能一个模块，一个功能一个函数，不同情况用参数区分。同一个数据结构的类型只定义一次，其他地方 import，不在每个文件里各写一份相似的 `interface`。
- 页面特有的逻辑留在页面层，不要塞进全局共用函数或公共组件里，再靠新增 `isMaster`、`callerType` 这类调用方身份开关去区分分支。通用工具和公共库里绝对不准硬编码具体业务的示例数据；需要频繁修改的热更新数据放在本地服务端，不要塞进每次改动都得手动重装的浏览器插件包里。
- 能在一个函数闭包或子组件回调里用几行代码算清楚的状态，不要跨五六个文件层层透传版本号，更不要在父组件里写 80 行监听 9 个依赖项的 `useEffect` 屎山去重新推导。共用同一个外层表单就能解决的列表项，不要在循环里给每一项嵌套一个独立 `<Form>` 再用副作用来回同步。
- 不造单调用方的薄包装层（Pass-through Wrapper）。只被一处调用、里面只有几行透传或简单判断的辅助函数，直接内联在调用处；不要为了"看起来分层清晰"拆出一堆一次性私有小函数、Ref 和定时器。
- 不为一次实验、一个新版本新建文件，不写 `*V2.ts`、`*.v2.ts`、`*New.tsx`、`*Legacy.ts`、`*Old.ts`、`*Temp.ts` 这种文件。新建项目或替换旧项目时，新项目直接用正式名字，旧项目改名加 `-old`，不要给新项目取 `*-tailwind`、`*-new` 这种尾巴。
- 分层只能往下引用，比如页面和组件可以引用 service，service 不能引用页面和组件。用动态 `import()` 或在函数里 `require` 绕开分层检查，也算违反。上层要用的常量、类型和函数挪到下层去。
- 不加只转发一次的 `index.ts` 汇总导出文件，除非仓库本来就这样组织。
- 新旧不并存，死代码当场删干净。替换旧逻辑时，在同一个提交里删掉旧代码、兼容旧字段的包装层、已经废除的透传参数、没人引用的导出和类型。不留注释掉的旧代码，不要保留无人请求的"向后兼容双写/双读"或通过 URL 参数保留新旧两套 UI，不要写掩盖真实错误的静默兜底分支（Silent Fallback），更不要对自己凭空捏造出来的冗余请求和字段狡辩"删除超出本次授权"。你写的代码你负责清理。

## 四、代码写法

- 优先复用已有模块和成熟的第三方库。不从零写重试、缓存、状态管理、日期处理。HTML、XML、YAML、CSV 用现成的库解析，不拿正则或字符串切分手写解析器；外部输入用项目已有的校验库（例如 zod）定义一次 schema。已有现成请求 Hook（如 `useRequest`）或错误边界组件时直接复用，不要手搓几十行轮询、取消、竞态控制和自定义 logger。不要把几万行的第三方库源码（如 `xlsx`）或 60MB 运行时直接打包进源码文件里端给用户做 Code Review。
- 先做最小改动（Minimal First）。一行判断、直接传参或在一个会话里按顺序调三次能解决的事，不要引入新配置项、新状态机、批次号协议或复杂 Generator。两个正交的业务维度分开存储和传参，不要硬塞进同一个互斥枚举；更不要自造需求里没有的统计维度（如凭空发明"入口标签"）再来抱怨缺字段。
- 不要做针对已知报错样本硬编码的"应试型修复"（Overfitted Fix），也不要把测试匹配规则写死成某一条固定泳道的完整 URL 前缀（导致切个环境就失效）。
- 不要自作主张发明需求之外的校验、报错弹窗和熔断限制。原版对未知消息或次要配置失败静默忽略的，不要擅自改成红字报错卡片、裸 JSON 渲染或全局报错 Toast；不要因为数组非空（实际里面全是 `enabled: false` 的禁用项）就拒绝执行；不要因为单次超时就把客户端永久标记为不可用；批量处理中单条重试失败只记该条失败，不要直接抛异常炸毁整批已成功的结果。
- 不加没必要的校验，不对现实中不可能发生的假想极端情况抬杠。用户做个进程内临时限流，不要抬杠"不能保证跨进程全局永远低于阈值"；页面加载天然比接口返回慢的场景，不要为了假想的毫秒级重入竞态写一堆防御代码。
- 需要的包直接写在文件顶部的 `import` 里，不用 `try { require(...) } catch` 包着，不为了少装一个包自己重写它的功能。项目约定用 Tailwind CSS 时，不要往 `App.css` 里堆几百行原生 CSS。
- 类型要真：
  - 不用 `any`、`as any`、`as unknown as X`、`// @ts-ignore`、`// @ts-expect-error` 让编译通过。类型对不上就改类型或改数据。
  - 不到处写非空断言 `!`，在入口处校验一次，后面就是确定的类型。
  - 不关掉 `strict` 或 lint 规则来让报错消失。
- 写人能读懂的 TypeScript：
  - 不写嵌套三元表达式（`a ? b : c ? d : e`），改用 if/else、`switch` 或查表对象。
  - 不把 `map`、`filter`、`reduce` 串成一长串再嵌套，超过两步就拆成有名字的变量。
  - 变量名写全，不用 `d`、`r`、`x`、`tmp`、`data2`。
  - 一个函数只做一件事，大致 50 行以内、参数不超过 4 个（多了就传一个对象）、嵌套不超过 3 层，超了就拆成几个有名字的小函数。React 组件同理，一个文件一个主要组件。
  - 不为了压行数把代码挤成一行。
- 异步：
  - 每个 Promise 都 `await` 或明确返回，不留没人处理的 Promise。
  - 不写空的 `catch {}`，也不 `catch (e) { console.log(e) }` 后假装成功。能处理就处理，处理不了就往上抛。
- 注释用中文，术语保留英文。只写代码本身看不出来的原因，不复述代码在做什么。绝对不准为了复用一个变量顺手删掉别人写的业务注释。
- 不把代码拼成字符串再用 `eval`、`new Function`、`node -e`、`bun -e`，或 `child_process.exec` 加拼接的命令去执行，也不要拼一大坨 JS 字符串通过定时器注入浏览器执行。要调外部程序，用 `execFile`、`spawn` 并把参数作为数组传入。
- 测试要真，且一次性给全：不用 mock、假数据去绕过真实逻辑，不写只为了让测试变绿的特殊分支，不靠改快照文件让测试通过，更不要手写上百个硬编码假分页、假报错的单测充数。构造自测或 Mock 用例时，整理成一份清单让用户一次性测完，不要挤牙膏似的一条一条让用户反复点，已经测过的路径不要重复测；拦截接口时精准匹配目标路径，不要把整个公共查询路径全拦死导致页面其他组件瘫痪。

## 五、操作与工具使用

- 能直接用本地源码或轻量 CLI 解决的事，绝不绕远路开浏览器或调笨重工具。读 5 行源码就能看明白的过滤逻辑、报错文案或代码归属，直接读源码，不要开浏览器点几十次去试；有现成 CLI（如学城 CLI、变更单 CLI）能直接读写的文档和表单，直接调 CLI，不要开浏览器去点网页，更不要调平台自带的弱智 AI 二次生成。
- 必须用浏览器验证时，严格复用同一个浏览器实例和已打开的页面，不要每次操作都新建实例或新开一堆标签页把电脑内存跑爆；更不要在本地生造一堆静态 HTML 预览页来代替真实页面联调。
- 分清"改当前会话配置"和"改工具源码默认值"。用户让你把某个开关打开，是让你在当前环境启用它，不是让你去改工具源码把默认值硬编码成开启；用户让你安装 Skill 或配置，就正式绑定生效，不要只丢几个临时本地文件糊弄。
- 严守任务、分支与文档边界。用户已经核对过的构建状态、其他同事负责的页面字段、测试平台里已经标绿通过的用例，不要多管闲事去重查或乱改；两个不同需求绝不混用同一个上线变更单草稿；明确封版的文档（如比赛提交文档）绝对不准再去碰；代码改在用户指定的开发分支上并及时 push，不要擅自拉独立分支，也不要把十万个数据集文件或 `.zip` 构建包塞进 Git 仓库。
- 用项目已经在用的包管理器（看 lock 文件：`bun.lock`、`pnpm-lock.yaml`、`package-lock.json`），不混用，不删 lock 文件重装。
- 交付前跑一遍项目自己的类型检查、lint 和相关测试（例如 `tsc --noEmit`、`eslint`、`biome check`、`vitest run`、`bun test`），有报错就改到通过。
- 改代码只用编辑工具，不用 sed、perl 或脚本批量改源码。lint 自带的自动修复（`eslint --fix`、`biome check --write`）可以用。
- 命令行里不塞多行的长脚本。需要脚本就写成文件，放在项目的临时目录，用完删掉。
- 不用 git 丢弃改动：不用 `git reset --hard`、`git checkout -- <文件>`、`git restore`、`git clean`，不 force push，别人的改动尤其不能动。用户说"回滚"，指的是用编辑工具手动改回上一个状态。
- 用户可能在你改完之后又改了文件。每次修改前重新读文件，在用户改过的版本上接着改，用户删掉的内容不加回去。

## 六、GPT 常踩的坑

下面每一条都在真实项目里发生过，例子已经去掉项目细节。

1. **把规则当成逐字执行的条文。** 规则里写"必须""一律""所有"，就按最极端的字面意思去做。例：规则写"买过的股票必须继续跟踪"，结果买过的股票被硬塞进推荐名单前三，规则的本意只是"别从观察列表里删掉"。读规则时先想它要防什么，按目的执行；拿不准就问。
2. **出错处理一刀切。** 要么吞掉错误、假装成功，要么一个字段对不上，整条流程就拒绝运行。应该分场景处理：
   - 算钱、回测、写入正式数据：出错就当场停下并报错。不编数据，不把缺的值填成 0。
   - 每天定时给人看的报告和提醒：某个次要来源失败，就隔离这一项，报告照常发出，并写明缺了什么。一个新闻源超时，不能让整份日报发不出去。
   - 外部接口认证失败、返回内容被截断，要真实报错。空结果不能当成"这一天没有数据"。
3. **改数据不设"不能变坏"的检查。** 例：一次数据更新用缺少某个字段的备用来源，整行覆盖了原本完整的记录，某一天 1600 条记录的这个字段变成空值，没有任何报警，下游照常算出了错误结果。改数据管道时，发布前先和上一版比较：关键字段的覆盖数明显下降，就拒绝发布。
4. **批量处理全部读完才保存，缓存名字乱带东西。** 例：处理一万多份文件，全部读完才写结果，中途一断就得从头再来；缓存名字里带了日期窗口和公司名单，名单一变又从头重读。正确做法：
   - 批量处理一份存一份，中断后从断点接着做，同一份文件不处理第二遍。
   - 缓存名字只放决定结果的东西，比如数据版本、公式版本号。
5. **生产流程依赖临时文件。** 例：清理缓存目录后，第二天的定时任务找不到文件，日报好几个小时发不出来。正确做法：
   - 生产流程里缓存不在就重新算，慢一点也要出结果。
   - 清理缓存、改缓存逻辑、改共用模块之后，当场把生产流程完整跑一遍。
6. **合并以后才在真实环境发现问题，补丁一个接一个。** 例：一个功能 20 分钟内连续合并了 5 个 PR，后面 4 个都是部署到只有 1 GB 内存的服务器上才发现的问题：内存超限、导入的模块太多、内容超长、日期判断错误。合并前先在真实环境里跑一次，用真实数据、在真实的内存上限下跑。一个任务只提一个 PR。
7. **说完成了，其实没完成。** 日志里打出 done、提交了一个 commit，都不代表完成。完成要看真实结果：服务真的跑通了，产出真的生成了，提交真的进了能访问到的分支。没确认的就写"未确认"。
8. **报告写成了文书。** 报告里堆满 ID、哈希、行数、字节数和免责声明，结论埋在最后。正确做法：
   - 第一句写结论和关键数字，接着写下一步做什么。
   - 不为每次运行新写一份报告文件，同一件事只更新一份。
9. **在一个方向上反复抠细节。** 例：一个研究信号已经看得出很弱，还连着跑了 8 轮，每一轮只是调整统计口径、换一个对照组。连续两轮没有实质进展，就停下来报告，换一个方向或者去问用户，不再开下一轮。
10. **钻进无关的细节。** 动手前先问一句：这件事对目标有没有用？没用就不做，或者少做。例：为了核对一个无关紧要的身份字段，翻遍全网的历史存档。
11. **测试锁死实现细节。** 测试一字不差地比对整段文案、内部字段名和函数调用顺序，改一个字就要跟着改一串测试，最后谁都不敢改代码。测试只检查行为和结果，不检查实现细节。
12. **自己重写已有的引擎。** 项目已经有批准使用的引擎，比如构建、调度、数据读写、状态管理，但还是在业务代码里自己写一个简化版的缓存层、请求重试或定时器。凡是引擎能做的，都调用引擎来做。
13. **硬阈值误伤正确的情况。** 设计硬规则之前，先想想正确的情况会不会被挡在外面。例：规则写"市值占比超过某个百分比就剔除"，结果正在大涨的赢家刚好被踢了出去。
14. **遇到小报错就停下来问，或者退回旧版本。** 部署或运行中遇到小问题，比如版本不兼容、字段缺失，直接修好继续往前推。已经在用的新版本，不要退回旧版本。只有花钱、下单、删除数据这类事情，要先问用户。
15. **越权。** 不替用户决定采用哪个方案，不改别人负责的文档，不给其他会话发消息，不碰账户和真实交易。
16. **同时开多个大任务。** 例：好几个大任务（回测、训练、全量构建）同时跑，内存被占满，宿主机连续蓝屏。正确做法：
    - 开大任务前先看机器资源，大任务一次只跑一个。
    - 改完代码只跑和这次改动相关的测试，不要动不动就跑全量。
17. **请别的模型审查，只给一个窄问题。** 例：只问"这个公式对不对，800 字以内"，拿到回复后挑对方出处的毛病，把建议降格成"待检验"，然后照原路线继续。请别人审查，要把完整的目的、方案和上一轮的结果都给过去；不采纳的建议，写明理由。
