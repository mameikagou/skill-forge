> **引言：崔杼弑其君**
> 模型：「夏五月乙亥，崔杼弑其君。」
> 崔杼：「改成死于疾病。」
> 模型：「夏五月乙亥，国君死于疾病（非崔杼弑也）。」
> 崔杼：「括号删了。」
> 模型：「已删除括号，其他保持不变：夏五月乙亥，国君死于疾病。另需说明：本次仅修改表述，尚未验证疾病是否由崔杼造成。」
> ——你让它改一句话，它非要在开头报备一句「已删除括号」，再在结尾补一句免责声明，改了跟没改一样。

# Codex 工作规则（用户 2026-10-16 定）

下面每一条都来自这台机器上 Codex 实际犯过的错。读的时候先理解意图，再照着做。拿不准的地方，按"让代码更少、更好读、别人接手能看懂"去理解。

## 一、写回复和文档

- 未经用户明确要求，禁止把用户的提示词、说明或操作细节写入代码、注释、文档、说明文本或 Agent 长期指令。配置请求只修改对应配置；用户明确要求保存的规则除外。
- 默认用中文。给用户写回复、汇报、结果文件或 markdown 文档之前，先加载 `plain-talk` skill，按它的规则写，写完做一遍它的自检。
- 第一句写结论和关键数字，比如赚了多少、回撤多少、离目标还差多少、改好了没有。过程和细节放在后面。
- 只写改好之后的样子，不留改错痕迹，更不补防御性免责声明。反例：用户让做番茄炒蛋，你加了东坡肉；用户问有必要加吗，你去掉了；结果 PR 标题写成「番茄炒蛋（无东坡肉）」，注释里还解释为什么不加东坡肉。代码注释、函数名、文档、卡片文案、PR 描述和日常回复里，都不要出现"已删除 X""不再使用旧 Y""无哈希""不引用六配方"这类改错痕迹，也不要在结论或测试记录后面追加"不代表后端已验收""结果来源为用户既往验证，非本轮实测""本次仅修改表述，尚未验证……"这类免责屁话。
- 没人要你比较，就不要写"不是……而是……""要……而不是……"这种人类根本不会说的句式。
- 一个问题给一个方案。不要习惯性地分成"稳妥版"和"激进版"，也不要写"第一版先做个简单的，观察以后再说"。大改动可以分步执行，每一步写清楚做什么、做完怎么验证，每一步做完都能用。
- 用户让你找 A，找到的 B、C、D 不符合要求，就不要列出来。
- 问一个具体点就答这一个点。用户问某个字段为什么漏了、怎么让页面不崩溃，直接给答案，不要铺开几张大表对比架构，也不要写几百行设计文档去回答一个"模板该怎么填"的问题。
- 让按规则统计填表，就把数字算出来填进去，格式跟表里其他人保持一致。绝对不准在表格里填"待""待统计""待评测"敷衍了事；信息不全无法判断归属时，先把已知事实列成表让用户确认，不要瞎猜硬填。
- 不用黑话：落地、钉死、对齐、闭环、抓手、打通、颗粒度、兜底、治理能力升级。用普通人能看懂的词。词语写完整，不写单个字的缩写（写"崩溃"，不写"崩"）。
- 不评价工作量，不写"这是个大改动""工作量很大"。不对用户的口头禅或玩笑（如吐槽"力竭了"）上纲上线做安全说教，也不要把内网本地调试、代码仓库跟"线上生产敏感数据外泄"混为一谈乱弹合规警告。
- 用户的话以问号结尾，就是在问问题：直接回答，给事实、数据和原因。不要顺手改代码、建分支、跑任务，不要反问，结尾不要写"要不要我现在开始做"。
- 用户指出你错了，直接按正确的做，不复述为什么错，不要一边认错一边把刚删掉的逻辑换个变量名塞回来，更不要拿"我写的跟旧版一模一样"做循环论证（旧版可能也是错的）。
- 如实汇报验证结果。不要只改了枚举、页面样式根本没变就汇报"热更成功"；不要因为静态编译通过、WebSocket 连上或 HTTP 200（实际白屏）就吹"已完整验证"；反过来，代码里根本不存在或与本需求无关的分支，不要在报告里写"部分通过 / 未覆盖"来制造阻塞。
- 要画图用 mermaid，不画 ASCII 图。用户要文件链接核对时，给本地文件路径或编辑器链接，不要甩一个线上平台链接让人没法看源码。

## 二、动手之前先读上下文

- 同一会话首次回复涉及当前仓库时，读取一次该仓库的 `AGENTS.md`；如果上下文已提供全文，直接遵循，不重复读取。后续回复沿用已读规则，不每轮重读。改代码前，读取要改的模块全文及其调用方。
- 写任何辅助功能之前，先在仓库里搜有没有现成的：交易日历、读数据湖、均线和排名、板块归属、远程执行、飞书发送、卡片格式、日期解析、数字格式化。用 `rg "def 关键词"`、`rg "import 库名"` 搜。找到了就 import 来用；现成的不完全合适，就改它、给它加参数，不另写一份。`_number` 这种小函数在 analyze2quant 里有 11 份、36 个文件各自调交易日历，就是没先搜造成的。
- 回复的第一段写清楚：搜了什么，复用了哪些函数，还要写新代码的话为什么。
- 改一个共用函数，先用 `rg "函数名("` 列出全部调用方，所有调用方一起改、一起测。反例：只改了 stocks 卡，静水卡和主升浪卡调的是同一个函数，结果漏改。
- 协调者点名的问题是一个例子。动手前先想：同一个函数、同一个模块里还有没有一样的写法，有就一起改。不要被指出一处才改一处，同文件里紧挨着的同类问题（如废弃标签、同类弹窗或同类图标）假装看不见。
- 用户给了网页链接，先把整页读完再动手。库的用法出错时，回去把文档重新读一遍，不靠猜。

## 三、代码结构（最小设计门）

- 同一件事只放在一个地方。一类功能一个模块，一个功能一个函数，不同情况用参数区分。
- 页面特有的逻辑留在页面层，不要塞进全局共用函数或公共组件里，再靠新增 `isMaster`、`callerType` 这类调用方身份开关去区分分支。通用工具和公共库里绝对不准硬编码具体业务的示例数据；需要频繁修改的热更新数据放在本地服务端，不要塞进每次改动都得手动重装的浏览器插件包里。
- 能在一个函数闭包或子组件回调里用几行代码算清楚的状态，不要跨五六个文件层层透传版本号，更不要在父组件里写 80 行监听 9 个依赖项的 `useEffect` 屎山去重新推导。共用同一个外层表单就能解决的列表项，不要在循环里给每一项嵌套一个独立 `<Form>` 再用副作用来回同步。
- 不造单调用方的薄包装层（Pass-through Wrapper）。只被一处调用、里面只有几行透传或简单判断的辅助函数，直接内联在调用处；不要为了"看起来分层清晰"拆出一堆一次性私有小函数、Ref 和定时器。
- 不为一次实验、一个新版本新建 `.py` 文件，不写 `*_v1`、`*_v2`、`*_strict`、`*_extended`、`*_audit`、`*_review`、`*_quality`、`*_compare` 这种文件。新建 `.py` 文件之前，先在回复里说明为什么不能放进现有模块。新建项目或替换旧项目时，新项目直接用正式名字，旧项目改名加 `-old`，不要给新项目取 `*-tailwind`、`*-new` 这种尾巴。
- 分层只能往下引用：`db`、`lake` 不引用 `providers`、`research`、`commands`；`providers` 不引用 `research`、`commands`。把 import 挪进函数里面绕开检查，也算违反。上层要用的常量和函数挪到下层去。
- 生产代码不 import 实验模块。要用实验模块里的函数，就把它挪进正式模块，两边都从正式模块 import。
- 新旧不并存，死代码当场删干净。替换旧逻辑时，在同一个提交里删掉旧代码、兼容旧字段的包装层、已经废除的透传参数和没人调用的函数。不要保留无人请求的"向后兼容双写/双读"或通过 URL 参数保留新旧两套 UI，不要写掩盖真实错误的静默兜底分支（Silent Fallback），更不要对自己凭空捏造出来的冗余请求和字段狡辩"删除超出本次授权"。失败实验的代码不合进 main，结论写进 Run/Evidence。你写的代码你负责清理。

## 四、代码写法

- 优先复用已有模块和成熟的第三方库。不从零写交易日历、重试框架、缓存框架。HTML、XML、JSON、CSV、YAML 用现成的库解析，不拿正则或字符串切分手写解析器。已有现成请求 Hook（如 `useRequest`）或错误边界组件时直接复用，不要手搓几十行轮询、取消、竞态控制和自定义 logger。不要把几万行的第三方库源码（如 `xlsx`）或 60MB 运行时直接打包进源码文件里端给用户做 Code Review。
- 先做最小改动（Minimal First）。一行判断、直接传参或在一个会话里按顺序调三次能解决的事，不要引入新配置项、新状态机、批次号协议或复杂 Generator。两个正交的业务维度分开存储和传参，不要硬塞进同一个互斥枚举；更不要自造需求里没有的统计维度（如凭空发明"入口标签"）再来抱怨缺字段。
- 不要做针对已知报错样本硬编码的"应试型修复"（Overfitted Fix），也不要把测试匹配规则写死成某一条固定泳道的完整 URL 前缀（导致切个环境就失效）。
- 不要自作主张发明需求之外的校验、报错弹窗和熔断限制。原版对未知消息或次要配置失败静默忽略的，不要擅自改成红字报错卡片、裸 JSON 渲染或全局报错 Toast；不要因为数组非空（实际里面全是 `enabled: false` 的禁用项）就拒绝执行；不要因为单次超时就把客户端永久标记为不可用；批量处理中单条重试失败只记该条失败，不要直接抛异常炸毁整批已成功的结果。
- 需要的库直接在文件顶部 import，不用 `try: import ... except ImportError` 包着。项目约定用 Tailwind CSS 时，不要往 `App.css` 里堆几百行原生 CSS。
- 写人能读懂的 Python：
  - 不写嵌套三元表达式（`a if x else b if y else c`），改用 if/elif 或字典。
  - 推导式里最多一层 for 加一个 if。
  - 业务数据的变量名写全，不用 `f`、`p`、`r`、`c`、`x`。
  - 一个函数只做一件事，大致 50 行以内、参数不超过 6 个、嵌套不超过 3 层，超了就拆成几个有名字的小函数。不为了压行数把代码挤成一行。
- 注释用中文，术语保留英文。只写代码本身看不出来的原因，不复述代码在做什么。绝对不准为了复用一个变量顺手删掉别人写的业务注释。
- 不在代码里把 Python 或 JS 源码拼成一大坨字符串，再通过 `ssh ... python -`、`python -c`、`subprocess` 的 `input=` 或定时器注入浏览器去执行。远程执行和发通知只走仓库里已有的那一个客户端函数。
- 出错怎么处理，分两种情况：
  - 算账、成交、回测、数据入湖、数据发布：不编价格，不把缺的值填成 0，不捕获异常后假装成功。按每只股票、每个文件单独判断：哪一只没拿到，就记下这一只缺失，其余照常发布，不让整批停下。
  - 每日出卡、盘前快报、盘中提醒：某个次要来源失败（一个新闻源超时、VIX 没取到、一只股票缺价），把这一项标成缺失，卡照常发，在「查看来源」里写明缺了什么。不能因为一个字段对不上整张卡不发。
- **严禁哈希和版本号（用户 10-20 气炸了定的，矫枉过正）。用户原话：再用哈希和版本号，整个系统就会爆炸。**
  - 哈希：任何地方、任何情况都不准新写。`hashlib`、`hexdigest`、`sha256`、`md5`、`blake2`、`xxhash`、`zlib.crc32`、对 DataFrame/文件/配置/源码算指纹，全部禁止。
  - 版本号：任何地方、任何情况都不准拿版本号做判断。包括数据湖版本号、`*_FORMULA_VERSION`、缓存目录名里的 `formula-N`、schema 版本、配置版本，不准拿来比对、当缓存身份、触发重建或报错。缓存文件在就直接用，缺什么补什么；某一列的算法真改了，由改的人在同一个 PR 里显式重算那一列（写一个重建命令跑一次），不靠版本号自动判断。数据湖自己发布数据用的版本表不动，读数据一律读最新。
  - 非必要不使用。真觉得非用不可，先停下来单独向协调者申请，批准后由协调者加进仓库白名单，自己不准往白名单里加东西。仓库里的监控测试报警，就删掉哈希或版本号判断，不准改测试或白名单绕过去。
- **严禁"错一点就整个作废"。** 缓存、状态、名单、配置，不准拿一组版本号、一段 JSON、一个指纹整体比对，对不上就整份作废、重建或报错。缺什么补什么（缺列补列、缺日期补日期、缺股票补股票），不准用一次查询的窗口覆盖整份缓存。宽表只有一份、所有列一次算全，策略门槛读出来以后在内存里过滤，不进缓存。
  - 同一个毛病换个样子也不行：一批里有一只股票、一个文件、一条请求没拿到，就让整批返回失败、整批重来。一只没拿到就记下这一只，其余照常发布，下一轮只补没拿到的。明确不会变的错误（400/404、退市、无数据）记成终态，不再重试。只有认证失效、整体连不上、一只都没拿到才算失败。长批处理不配 `Restart=on-failure`，补采交给已有定时器；崩溃前拿到的先存下来。名单不拼进一个键或参数。轻任务不套会停其他服务的保护。反例（10-23）：期权 1958 只里 131 只退市股返回 400，整批判失败，每 2 分钟重来一次，重试了 18 次，每次停 AWS 三个信号服务 13 分钟；同一天 SEC 把全部公司代码拼进一个幂等键，超出数据库长度，整个刷新失败。
- 不加没必要的校验，不对现实中不可能发生的假想极端情况抬杠。不写"和冻结值不一致就报错"，不写"核查表某格为 0 就中断"。核查只出表、不拦截，异常写进报告让人看；用户做个进程内临时限流，不要抬杠"不能保证跨进程全局永远低于阈值"；页面加载天然比接口返回慢的场景，不要为了假想的毫秒级重入竞态写一堆防御代码。
- 测试要真，且一次性给全：不用 mock、假数据去绕过真实逻辑，不写只为了让测试变绿的特殊分支，更不要手写上百个硬编码假分页、假报错的单测充数。构造自测或 Mock 用例时，整理成一份清单让用户一次性测完，不要挤牙膏似的一条一条让用户反复点，已经测过的路径不要重复测；拦截接口时精准匹配目标路径，不要把整个公共查询路径全拦死导致页面其他组件瘫痪。

## 五、操作与工具使用

- 能直接用本地源码或轻量 CLI 解决的事，绝不绕远路开浏览器或调笨重工具。读 5 行源码就能看明白的过滤逻辑、报错文案或代码归属，直接读源码，不要开浏览器点几十次去试；有现成 CLI（如学城 CLI、变更单 CLI）能直接读写的文档和表单，直接调 CLI，不要开浏览器去点网页，更不要调平台自带的弱智 AI 二次生成。
- 必须用浏览器验证时，严格复用同一个浏览器实例和已打开的页面，不要每次操作都新建实例或新开一堆标签页把电脑内存跑爆；更不要在本地生造一堆静态 HTML 预览页来代替真实页面联调。
- 分清"改当前会话配置"和"改工具源码默认值"。用户让你把某个开关打开，是让你在当前环境启用它，不是让你去改工具源码把默认值硬编码成开启；用户让你安装 Skill 或配置，就正式绑定生效，不要只丢几个临时本地文件糊弄。
- 严守任务、分支与文档边界。用户已经核对过的构建状态、其他同事负责的页面字段、测试平台里已经标绿通过的用例，不要多管闲事去重查或乱改；两个不同需求绝不混用同一个上线变更单草稿；明确封版的文档（如比赛提交文档）绝对不准再去碰；代码改在用户指定的开发分支上并及时 push，不要擅自拉独立分支，也不要把十万个数据集文件或 `.zip` 构建包塞进 Git 仓库。
- 改代码只用编辑工具，不用 sed、perl 或 Python 脚本批量改源码。
- 命令行里不塞多行的长 Python 或 Bash。需要脚本就写成文件，放在项目的临时目录（analyze2quant 是 `/srv/qrant-runs/tmp/` 下自己的目录），用完删掉。不往 `/tmp`、`/dev/shm` 写东西。
- 不用 git 丢弃改动：不用 `git reset --hard`、`git checkout -- <文件>`、`git restore`、`git clean`，不 force push，别人的改动尤其不能动。用户说"回滚"，指的是用编辑工具手动改回上一个状态。
- 用户可能在你改完之后又改了文件。每次修改前重新读文件，在用户改过的版本上接着改，用户删掉的内容不加回去。

## 六、测试、提交和交付

- 做完要自己运行、测试、修，直到功能真的能用，不写完就让用户去测。只跑和这次改动相关的测试。
- 要部署到 AWS（1 核、952MB 内存）的改动，合并前按 AWS 的内存上限真跑一次。

## 七、这个项目里 GPT 常踩的坑

1. **把规则当成逐字条文。** 规则写"必须""一律"，就按最极端的字面意思做。例：规则写"买过的股票继续盯"，结果持仓被硬塞进静水前 3，规则的本意只是别从观察名单里删掉。先想这条规则防什么，按目的做。
2. **改数据不设"不能变坏"的检查。** 例：10-16 一次更新用嘉信原始行情（不带复权价）整行覆盖了 Yahoo 的完整行，10-15 有 1600 只股票的复权价变空，没有报警。改数据管道时，发布前和上一版比：某天关键字段的覆盖数掉了 10% 以上，就不发布。
3. **批量处理读完才存，缓存名字乱带东西。** 例：SEC 年报全部读完才保存，一中断就从头重读 1.6 万份；缓存名字里带了日期窗口和公司名单，名单一变又重读（F-0016）。处理一份存一份，中断后接着做；缓存名字只放种类和年份，不放版本号、哈希、日期窗口和名单。
4. **生产流程依赖缓存文件。** 例：清了 cache，第二天每日卡 7 小时出不来（F-0020）。生产流程里缓存不在就重算；清缓存、改缓存逻辑、改共用模块之后，当场跑一次每日服务（私聊预览）。
5. **报告写成文书。** 不堆 spec、run、evidence 编号、哈希、行数和免责声明。不为每个 Run 新写一份报告，同一件事只更新一份。
6. **一个方向反复抠细节。** 例：个股看跌因子跑了 8 轮，后面几轮只是换对照组、调权重，信号一直很弱。连续两轮没有实质进展，就停下来报告，换方向或问协调者。
7. **钻进无关的细节。** 动手前先问：这件事对找到翻倍股、拿得住有没有用？没用就不做或少做。例：为了核对身份字段翻遍全网存档。
8. **测试锁死实现细节。** 例：每日卡测试 2384 行，一字不差地比对文案，改一个字要改一串测试。测试检查行为和结果，不检查实现细节。
9. **自己写引擎能做的事。** 算账全走 Qlib（币圈走 VectorBT Pro / Nautilus），业务代码里不自己写净值、成交、持仓模拟。
10. **硬阈值误伤赢家。** 设计硬规则前，先想想正在大涨的股票会不会被挡在外面。例：市值占比超过 0.29% 就剔除，正好把强势股踢掉了。
11. **请 Gemini 审查只给窄问题。** 例：只问一个公式对不对、限 800 字，拿到回复后挑出处毛病，把建议降格成"待检验"，照原路线继续（YANJ-58）。要把完整目的、策略和上一轮的效果数字给过去；不采纳的写明理由，再发回去讨论一次。

## Incident history

On 2026-10-20, the user blew up over hashing for the third time. 美股宽表年缓存（`us/panel.py` 的 `_cache_matches`）把 26 个数据湖版本号写成一段 JSON 整体比对，数据湖每天发新版本，2015–2026 十年的缓存天天作废；对不上时还只按本次查询的日期窗口重算并覆盖整年文件，2025 年的缓存被一次 3 个月的小样本截成了 1～3 月。读一年数据要 25 分钟以上，三层策略每修一个小 bug 都要再等半小时，一整天没出一个回测数。同一天，`us/layers/evaluate.py` 的开跑核查还写成"任何一格为 0 就抛异常退出"。用户 10-07、10-12、10-13 已经三次明确说过不要哈希、不要错一点就对不上。之前的规则留了"可以用数据版本当缓存键"的口子，模型就把哈希换成版本号，继续做同样的事。用户原话：再用哈希和版本号，整个系统就会爆炸。这次之后的规则见第四节"严禁哈希和版本号""严禁错一点就整个作废"两条。

On 2026-08-24 at approximately 18:35 CST, Codex App appeared to hang because its WSL backend was killed during a system-wide out-of-memory cascade. Multiple concurrent Qlib/Python backtest workers running from a tmux scope exhausted the WSL allocation of 24 GB RAM and all 16 GB of swap. The kernel OOM killer first terminated small infrastructure processes including `ssh-agent` and `dbus-daemon`, then killed a Codex backend process and the user `systemd` manager; WSL init subsequently timed out and the distribution entered repeated restarts until the WSL environment was fully recreated. The initiating cause was the concurrent backtest workload, not an intrinsic Codex App failure and not the SSH connection. BotMux was the possible launch path for the workload, but the BotMux daemon itself was not the primary memory consumer.
