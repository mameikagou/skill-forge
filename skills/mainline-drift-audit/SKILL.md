# 主线漂移审查

默认只读：找证据、报问题。用户明确要求时才改、删、提交。

## 先认清唯一主线

先读仓库 `AGENTS.md`（职责地图、谁负责什么）和相关代码，列一张小表：这件事的唯一实现在哪、入口在哪、权威数据在哪、允许写到哪。认不出唯一主线，这本身就是第一个问题，不要自己发明一套架构。

analyze2quant 当前事实（以 `AGENTS.md` 为准，冲突时听它的）：

- analyze2quant 是唯一主线：一个 Python 包、一个 CLI/API、一个研究页面、一条 PostgreSQL 迁移链。旧 analyze 只读，它的 `.planning/`、错题本和人写的报告是要保留的历史证据。
- 数据源归 providers，发布归 lake，算法归 research，参数归 spec，命令归 commands/cli，基础设施归 infra。`tests/test_repository_map.py` 要求每个文件在职责地图里有主人。
- 研究和回测：A 股、美股用 Qlib，币圈用 VectorBT Pro/Nautilus。成交、持仓、现金、费用、收益都归引擎。
- 每日候选只由 `us_growth_discovery_watch.combine_watch` 产出；在线页面和卡片读 PG 缓存，湖是正本。

## 要找的问题

**另起一套**
- 已有主线能做的事，又新建了引擎、CLI、数据库、注册表、配置根、结果目录或报告体系。"临时""轻量""只是研究用""兼容"都不是理由。
- 自己写了现金、持仓、成交、费用、净值、收益的计算，代替正式引擎。
- 研究改进（持有规则、因子、模型）没有加在现行策略上，而是另起候选名单、另训排序、另开账户，再单独和指数比。例：利弗莫尔拿法装在临时"价格前 10"上，而每日卡用的是另一套排名。
- 运行时绕开数据湖，直接从外部拉数据。
- 同一份结果同时写进 JSON、YAML、Markdown、CSV、Parquet、数据库里的好几处，谁是权威说不清。

**只加不删**
- 每批一个新模块（`*_v1`、`*_extended`、按日期或批次命名的文件），失败实验、已停线的代码留在 `src/`。
- 新路径上线了，旧入口、旧配置、旧测试还活着，"先兼容着"没有删除时间。
- 测试在保护错误的结构（断言重复文件、并行入口存在），或只检查文件生成了，不检查结果对不对。

**过度工程**
- 严禁哈希和版本号（用户 10-20 定）。哈希、指纹、版本号（数据湖版本、`*_FORMULA_VERSION`、缓存目录里的 `formula-N`、schema/配置版本）拿来比对、当缓存身份、触发重建或报错，都算问题。只有仓库白名单里的地方可以用：数据湖发布、外部原始文件核对、下单和推送防重复。缓存在就用、缺什么补什么；"一组版本号或一段 JSON 对不上就整份作废"是严重问题。审查时跑仓库的哈希和版本号监控测试，并 `grep -rn "hashlib\|_VERSION\|_cache_matches\|version_id" src/`，白名单以外的全部列出来。
- 大段预先登记、审计面、权限层、封存机制，占的时间比实验本身还多。

**产物和磁盘**
- 每次运行复制整份源数据、宽表或模型输入；大中间文件没有清理时机；失败实验和采用结果留着一样大的产物。
- 临时文件写到 `/tmp`、`/dev/shm` 或仓库里，没有用受管的 `/srv/qrant-runs/tmp`；路径拼错在输出目录里套出 `home/...`。

**删错东西**
- 清理时把 `planning/`、错题本、人写的研究结论和报告、数据湖、对象存储、数据库记录、已应用的迁移，和可重建的缓存一起删了。这些要保留，过时的标注"已取代"并链接新路径。

## 方案审查（还没写代码时）

逐条核实方案的说法，不信方案自己的描述：

- "现在没有这个能力"要有现有代码的证据；
- "复用了主线"要能画出从入口到引擎的完整调用链；
- "临时的"要写明删除时间和条件；
- "可重建"要写明权威来源和重建方法。

列出方案新增、复用、删除了哪些东西（引擎、包、CLI、数据库、配置、产物目录、报告、测试）。新增必须说明为什么放不进现有的；替换了旧路径，就在同一个方案里删掉旧的。

每个要落盘的东西先说清谁读它；没有读者的不落盘。

## 实现审查（看 diff 时）

先看本次改动，再扫全仓。对每处新增问：现有主线能不能做？是不是现有状态的第二份？是长期代码还是一次性实验？测试验证的是行为还是文件？也要报告方案里承诺删除、实际没删的。

机械扫描（只读，结果要逐条打开源码核实，不能直接当结论）：

```bash
python3 <skill-dir>/scripts/scan_repo.py <repo-root>
```

## 报告

在对话里直接报，不另写审查文档。按严重程度排：

- `P0`：假的正式结果、数据损坏或丢失、未来数据、危险的删除；
- `P1`：并行引擎或主线、无限增长、写出受管目录、假的生产入口；
- `P2`：重复的入口、配置或存储，陈旧代码，重复产物；
- `P3`：命名、小残留、文档整洁。

每条写：具体文件和行或目录；绕开或重复了哪条主线；影响；怎么处理（删、并进主线、改成临时、保留）；用什么最小的检查防止再犯（代码断言、职责地图测试、白名单、清理规则）。

最后一行给结论：`主线 PASS/BLOCKED`、`现在删除：<具体目标或无>`、`保留：<受保护的目标>`。

防复发优先加一个最小的、能自动失败的检查，不为了守规则再建一套管理框架。
